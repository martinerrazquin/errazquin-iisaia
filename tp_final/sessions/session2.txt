● You can make the frontend look good without touching the CSP. The restriction
  is much narrower than the spec note suggests. I tested it in Chromium with the
  exact production style-src 'self' policy, using real Radix components and the
  sonner toast library (a scratch build, not in the repo).

  What the strict CSP actually blocks

  ┌──────────────────────────────────────────┬──────────────────────────────┐
  │            Styling technique             │    Under style-src 'self'    │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ CSS files built by Vite (Tailwind, CSS   │ ✅ works                     │
  │ Modules, plain .css)                     │                              │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │                                          │ ✅ works. React sets styles  │
  │ React's style={{...}} prop               │ through JavaScript, which    │
  │                                          │ the CSP doesn't police.      │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ Radix popover/select/dropdown            │                              │
  │ positioning (the "inline styles" the     │ ✅ works for the same reason │
  │ spec worried about)                      │                              │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ Self-hosted fonts (@fontsource/*         │ ✅ works                     │
  │ packages), SVG icons (e.g. lucide-react) │                              │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ A style="..." attribute written into     │ ❌ blocked                   │
  │ HTML                                     │                              │
  ├──────────────────────────────────────────┼──────────────────────────────┤
  │ A <style> tag injected at runtime        │ ❌ blocked                   │
  └──────────────────────────────────────────┴──────────────────────────────┘

  In practice, only libraries that inject <style> tags at runtime break. In my
  test that meant three things:
  - Radix Dialog / modal menus: the page behind an open modal can still scroll.
    It's cosmetic and everything else works.
  - Radix Select: a small scrollbar-hiding rule is lost. Cosmetic.
  - sonner (toasts): it loses all its styling. The fix is to import its bundled
    sonner/dist/styles.css file directly.

  Options that work with the current CSP

  1. Tailwind CSS v4. It generates one static CSS file at build time. Fully
     compatible, and it's the base for most modern React styling.
  2. shadcn/ui (Tailwind + Radix). This is what the spec planned, and it's
     viable. You get polished buttons, inputs, cards, tables, dialogs and
     toasts. The only cost is the cosmetic issues above, which you can live with
     or fix (see "Middle ground" below).
  3. DaisyUI. A Tailwind plugin made of pure CSS components with no JavaScript,
     so it has zero CSP issues. Less refined than shadcn but very fast to apply.
  4. Pico CSS (or Simple.css / Water.css). These style plain HTML elements
     automatically. The app already uses plain <label>, <input>, <button> and
     <table>, so importing one file gives a big improvement in about an hour.
     Fully compatible.
  5. Mantine v7+ or React Aria Components. Fuller component libraries that use
     static CSS or style props. They're probably fine, but I didn't test them.
  6. Avoid: libraries that generate CSS at runtime (styled-components, Emotion,
     and therefore MUI and Chakra by default). They inject <style> tags and
     break under this CSP.

  My recommendation: Tailwind v4 + shadcn/ui, with sonner's CSS imported
  statically. If you want the quickest visible win with no risk, start with Pico
  CSS.

  Middle ground

  Modern CSP can treat the two blocked cases separately. One option is to allow
  style="..." attributes while still blocking injected <style> tags. That
  doesn't fix the issues above, since those are all injected <style> tags. The
  fix that keeps the CSP strict is a per-request "nonce" (a random token that
  marks a <style> tag as approved). Radix supports it, but our server currently
  serves index.html as a plain file, so that would mean extra Caddy setup. I
  don't think the fix is worth that work.

  If you relax it (style-src 'self' 'unsafe-inline')

  What style-src 'self' protects here: it stops CSS that an attacker manages to
  inject from running. In theory, injected CSS can do two things:
  1. Leak data by making the browser load an attacker URL. This is already
     blocked by the other rules (img-src, font-src, connect-src and default-src
     are all 'self').
  2. Change what the page looks like, for example hiding the one-time-view
     warning or faking content.

  Either way, the attacker first needs a way to inject markup. React escapes all
  text, and the frontend has no dangerouslySetInnerHTML or innerHTML.

  Pros of relaxing: every styling library works with no workarounds and no
  console warnings.

  Cons:
  - Weaker defense in depth. The remaining risk is someone changing the page's
    look, which is small for this app.
  - Spec deviation. §27 of the spec mandates style-src 'self' and the prod smoke
    test checks for it. Since this is a graded project, that's probably the
    biggest real cost.
  - Security scanners and audits often flag 'unsafe-inline'.

  What must not be relaxed is script-src 'self'. The decryption key lives in the
  URL fragment, so injected JavaScript means stolen secrets. That rule is the
  one doing the real protecting.

  Bottom line: keep the CSP. You don't need to relax it to get a polished UI.

  it asks clarifying questions, proposes 2–3 approaches and waits for your

     rounds, save the chosen look as a short style guide in
     docs/superpowers/specs/.
  4. Implement. Plan it with superpowers:writing-plans, then restyle the real
     app one page at a time. Check it with the run skill (screenshots of the
     real app) and the Playwright tests, including the CSP smoke test.

  I'd start with OpenPage (/s), the page with the most going on. The other pages
  can then follow the style you pick.

  ▎ strict CSP, no CDNs, Tailwind v4 + shadcn/ui, Spanish text. Start with /s

  right there doesn't prove it will work in the app. The real check is step 4,

● 1. Checking CSP compliance without waiting on production builds

  Yes, and you don't have to do the waiting. Split the loop in two:

  - You look at the page in npm run dev. It reloads instantly. For judging
    looks, dev is fine.
  - I check CSP compliance after each change I make. A small script, e.g. npm 
    run csp-check, runs a production build (a few seconds for this app). It
    serves the result with the exact prod CSP header and opens the pages in a
    headless browser. It fails if the browser reports any CSP violation. It's
    the same test I ran earlier, about 10–15 seconds per check, and you never
    need to switch modes.

  A grep of the build output for patterns like createElement("style"),
  setAttribute("style" or innerHTML is a useful extra, but it's not enough
  alone. It flags code that never runs and misses indirect cases, so I'd use it
  as a hint only.

  Two details make this cheap in practice:
  - Violations can only come from a few places: a new library that injects
    <style> tags, or a hand-written style="..." attribute. Tailwind classes and
    .css files can't violate the policy. The real risk shows up mostly when a
    dependency is added.
  - The check can only see the states it can reach. Without logging in, it
    reaches little beyond the login prompt and error screens. A dev-only page
    that renders each page's states with fake data fixes that. The same page is
    also handy for you to look at every state at once without clicking through
    real flows.

  2. Superpowers or not

  For this loop, skip brainstorming. It's built for one-shot design → spec →
  plan → implement, and your loop is short tweak-and-reload rounds. Its
  question-asking and spec-writing would just slow each round down. The
  superpowers plugin pushes skills by default, but your instructions override
  it. Just say "no brainstorming, we're iterating."

  Suggested workflow:
  1. Setup, one time. Add Tailwind + shadcn/ui, the fake-data states page and
     csp-check.
  2. First page. Iterate: "make the header darker", "more spacing in the form",
     and so on. I edit, run csp-check, you reload.
  3. When the page converges. Ask me to pull the reusable pieces out: the
     color/spacing settings in the Tailwind theme, and shared components like
     Button, Card, Alert. Also have me write a short docs/ui-style.md with the
     conventions. The code itself then carries the style.
  4. Next page, in a new session. "Restyle /admin following docs/ui-style.md and
     the components in src/components/ui. Run npm run csp-check after each
     change." That puts the style in the new session without relying on old chat
     history.

  If you want, I can do the setup step now.

● /_estados is a page inside the frontend app, not a backend endpoint, and it
  only exists in dev and csp-check builds. It still has two jobs now that the
  restyle is done:

  1. It gives csp-check access to the states behind login.
     - On the real routes, the headless browser in csp-check only reaches what a
       logged-out visitor sees: the login prompts, the invalid-link error and
       not found.
     - Through /_estados it also loads the create form, the created links, the
       revealed secret, the admin table with its open recipient rows, and so on,
       all under the exact production CSP.
     - That's what would catch a future library or component that injects styles
       only in one of those states.
     - The other tests don't cover this. The dev e2e runs under the relaxed dev
       CSP. The production smoke test only goes through create → reveal, so it
       never sees the admin table or the error states.
  2. It's a review page for future UI changes. Every state of every page is on
     one screen with fake data, so you don't have to log in as several users,
     create shares or let them expire. That's how we iterated this time, and it
     works the same way for the next change.

  What it costs:
  - It's never shipped: it's left out of the production build, which I checked
    in the production bundle.
  - It needed small additions to the app code: the optional fragment /
    initialPhase props on OpenPage, the AdminView split, and the exported
    CreatedLinksView.
  - When a page gains a new state, someone should add it there too.

  My recommendation is to keep it, mainly for the first job. If you remove it,
  csp-check falls back to checking only the logged-out screens.
